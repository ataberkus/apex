# Native Windows milestone

Current scope: a native Windows daily-driver, not Harbor/Terminal-Bench completion. WSL, Docker, Linux image digests and Harbor are **not runtime prerequisites** for this milestone. Original benchmark criteria, frozen data and spending restrictions remain intact.

## Requirements and checks

- Native Windows [Bun](https://bun.sh) >=1.4.3 and pinned Pi 1.4.0. Node is not needed: `bin/apex`, the dashboard (`bun run dashboard`) and every Pi child run on the Bun executable that started them. A dashboard that outlives its `bun.exe` (Bun reinstalled or moved) falls back to `bun` on PATH; with neither, a session stops with "Bun was not found at …". A workspace folder that was moved or deleted is refused with "The folder … does not exist" instead of starting an agent (libuv reports a missing working folder as `spawn <runtime> ENOENT`, naming the runtime).
- Git for Windows/Git Bash, ripgrep (`rg.exe`) and fd (`fd.exe`) on the PATH the launcher inherits. Preflight checks that PATH only; a workspace `.tools/bin` is not counted. One working setup: copy `rg.exe`/`fd.exe` to `%LOCALAPPDATA%\Apex\bin` and append that folder to the user PATH (new shells pick it up).
- Windows PowerShell 5/.NET Framework, FullLanguage and permission to execute the bundled private-storage helper. Apex does not bypass execution policy. RemoteSigned refuses the unsigned helper whenever Windows treats it as Internet-zone: a download mark (`Unblock-File`) or a Low integrity label inherited from a sandbox-labelled checkout (`icacls <script> /setintegritylevel M`; Git re-creates changed files with the inherited label). A refused helper fails closed and its error names the executable, script and command to run.
- Checkpoints are captured only before tools that may change the working tree; `todo`, `contract`, `explore` and `verify` never capture, so a checkpoint failure cannot block them.
- Checkpoints additionally require a real local Git repository in the task folder. Their shadow store sits under `.apex/checkpoints/<64-character key>/shadow`; Git cannot run from a working directory past 246 characters, so project roots longer than about 156 characters fail closed with `path-too-long` (Apex already enables `core.longpaths` and relative shadow paths).
- A selected feature that fails to start stays alone: later features still register, and an error naming it appears as a notification (on stderr in print mode). Failed `checkpoints` keep blocking mutating tools with `Checkpoint failed; mutation blocked: <reason>`, a failed `safety` blocks every tool, and any other failed feature is off. Tree navigation and forking retry the setup.
- Python/uv/source-pinned Harbor remain development dependencies for the **full** historical test/check commands, not the native launcher.

From PowerShell or Git Bash in this source folder:

```powershell
bun install --frozen-lockfile --ignore-scripts
bun run preflight:windows
bun run check:windows
bun run test:windows
bun run micro:windows
bun run smoke:windows-package
```

To start Apex from cmd in any folder, run `install-apex.bat` from this checkout once, then open a new cmd window. It appends `<checkout>\bin` (with the `apex.cmd` shim) to the user PATH by editing `HKCU\Environment` with the value kind kept, not with `setx`, which truncates at 1024 characters. `apex` then runs `bun <checkout>\bin\apex` without changing folder, so the folder you `cd` into is the task folder, and every argument passes through. That includes `apex --session <id>` below. If Bun is missing the shim prints the same setup message as `start.bat` and exits 1. `dashboard.bat` starts the web dashboard and `start.bat` runs terminal Apex on the checkout itself; both can be double-clicked. These launchers are checkout conveniences and are not packaged: a package install gets Bun's own `apex.exe` shim from `bin/apex`.

`preflight:windows` is read-only: no credentials, model catalog requests, installs, Python or Docker probes. `check:windows` parses JavaScript with Bun's transpiler (Bun has no `--check`), and validates source JSON, package resources and the native prerequisites without running Python. `test:windows` runs the suite with `bun test` (two isolated workers, preloading `scripts/live-builtins.mjs` so fixtures can replace builtins such as `child_process.spawn` the way Node's `syncBuiltinESMExports()` allowed) and retains explicit capability skips. Set `APEX_TEST_PARALLEL` (1–16) to change the worker count; Linux defaults to up to four, while Windows keeps two until a native run confirms the fixture watchdog margins; use `bun run test:windows`, not bare `bun test`, which skips that preload. The original `bun run test` still includes Python/Harbor analysis tests. `micro:windows` exercises tools, transcript restoration, context, core controls, daily-driver commands and offline feature composition on the Windows default model (`default` contract: Claude Opus 5.5 at medium). It records `validation/windows-native-micro.json` separately. A PASS here is **only Windows-native mechanics acceptance**; the original `bun run micro` and `validation/offline-micro.json` retain their broader scope and Unix process blockers.

`smoke:windows-package` packs the source with `bun pm pack` and installs that tarball with the **exact pinned Pi peer** in a fresh temporary prefix. It copies the peer's and Apex's runtime subtree of the root `bun.lock` (entries reachable through Bun's nearest-first nested keys; dev-only test tooling is pruned) into a `bun.lock` there, after checking the source lock pins Pi at the launcher's version with a sha512 integrity hash, installs it with `bun install --frozen-lockfile --offline`, then adds the Apex tarball with `bun add --exact --offline` and verifies the installed Pi integrity. It uses only Bun's existing package cache (`bun pm cache`), disables lifecycle scripts, tests Bun's generated `apex.exe`/`apex.bunx` shim (it runs the packaged `bin/apex` with `bun` from PATH) through real PowerShell, cmd and Git Bash calls, and packaged native output recovery, then removes the prefix. No dependency junction is used. Packages missing from Bun's cache produce BLOCKED with their names in `missing_from_bun_cache`, not an online fallback; fill the cache once with a normal online `bun install --frozen-lockfile` in this folder. This is not a global installation.

## Windows selection

Plain `apex` on native Windows runs Claude Opus 5.5 (`anthropic/claude-opus-5-5`, Claude Pro/Max login) at medium thinking and applies `WINDOWS_AUTO` from `lib/windows-target.mjs` (see README "Native Windows"): only features that add no prompt sections, tools or continuations, namely context `cache`, core `correct` and features `cost`, `plan`, `report`, `resume` and `autocompact`, with `checkpoints` only at a Git repository root. `--profile headless` adds no Apex feature; core `headless` is opt-in, because its prompt section cost more without a measured benefit (ab-008–ab-010 in `DECISIONS.md`). The private `.apex/` folder holds its own `.gitignore` (`*`), so Git skips it, but `ls` still shows it. An explicit `--apex-context`/`--apex-core`/`--apex-features` selection replaces the defaults and keeps the Windows target (the launcher adds `--apex-target windows`) unless it names a Muse model (`--provider openrouter|apex` or a Muse `--model`); `--apex-target` and `--apex-eval` invocations pass unchanged. `--apex-off` runs stock Pi, which a Claude subscription refuses (Anthropic answers that third-party apps draw from extra usage); for a plain agent on Claude use the bare `apex --apex-target windows`, which loads no Apex feature, only the Claude Code identity rewrite. Non-Windows invocations are unchanged. Inspect an explicit configuration without inference:

```powershell
bun bin/apex --apex-dry-run --apex-target windows --profile headless --apex-context "read,search,edit,shape" --apex-core "todo,verify" --apex-features "cost,checkpoints,plan,report" "Inspect this project"
```

`--apex-target windows` belongs in the Apex option prefix. It requires native Windows and selects exact `anthropic/claude-opus-5-5` by default. An explicit `--provider` of `openai-codex`, `anthropic` or `opencode-go` with a plain catalog `--model` id selects that model instead. Thinking defaults to medium; `--thinking` can choose any level, except with eval isolation or the auto route, which stay at xhigh. API-key overrides, other providers, fallback lists, `:thinking` suffixes and model scopes other than the chosen `provider/model` are rejected. The target always loads `extensions/apex-router/claude-identity.mjs`, which makes Pi's system prompt acceptable to a Claude subscription. OAuth logins and the saved OpenCode Go key stay in a private Pi agent directory outside the project/package (`%LOCALAPPDATA%\Apex\sol-oauth`, shared with the dashboard; Pi refreshes an expired Claude token itself). The launcher selection is **not an OAuth credential validator, OS sandbox or provider-side spending cap**; it does not authenticate or reserve funds during dry-run. Ordinary non-dry-run prompts can consume account allowance.

Budget policy. Daily Claude, Codex and OpenCode Go use has no Apex dollar cap; usage estimates stay visible (`/cost`, the dashboard) and provider limits apply. Automated or scripted live acceptance runs on Claude are recorded in `evals/claude-budget.json`, capped at **$10 catalog estimate** for the 2026-10-19 Windows acceptance (`spending_policy: capped`); every run there also needs bounded scope and physical request/usage/deadline limits. `evals/codex-budget.json` is the Codex usage history; its earlier $20 cap was removed and it records no limit. OpenRouter spending remains frozen. The offline Windows gates read no credentials and spend nothing. Auxiliary inference (independent `/review`, `verify`/`explore` subagents, the context `compact` flag's inferred summaries), max/recovery and automatic `apex resume` launch remain denied by the original offline policy. These are not denied: `/plan` (it starts no model request itself; your next message runs as an ordinary turn with read-only tools and its final answer is saved to `PLAN.md`), literal `/plan save`, session inspection, native completed-transcript restoration and `autocompact`, which is Pi's own compaction on the session model.

The dashboard uses the same selection: a session on a signed-in model (Claude, Codex, OpenCode Go) starts with `--apex-target windows` at the thinking level you pick (medium by default), and the New session dialog disables the unavailable route/output/bg/max/recovery flags. Its default model is Claude Opus 5.5 at medium and its default preset is `WINDOWS_AUTO` (checkpoints only at a Git root). Plain agent on a signed-in model runs the bare Windows target (no Apex feature); on Muse it passes `--apex-off`. Selected safety prompts in both the terminal UI and dashboard sessions (Allow/Deny dialog; the dashboard adds Allow all in this session and an Auto-approve toggle).

**Model pair.** `--apex-pair PLAN,BUILD` selects the virtual model `apex/pair` (`extensions/apex-router/pair.mjs`). PLAN is `provider/model:level` and BUILD is `provider/model[:level]`, for example `bin/apex --apex-target windows --apex-pair anthropic/claude-opus-5-5:high,anthropic/claude-sonnet-5-5:medium`. Both models must be in the catalog of a Windows login (Codex, Claude, OpenCode Go) and support the level you give; the providers may differ, and each needs its own sign-in. Leave out `--provider`, `--model` and `--models`. The build level comes from the spec or `--thinking` (not both) and defaults to `medium`; it is the session thinking level, so it can change in Pi or the dashboard while the planning level stays fixed. Each message you write is planned by the planning model. After the first successful `edit`/`write`/`apply_patch` of that request, the build model continues. Three failed tool calls in a row on the build model hand the rest of the request back to the planning model. A request switches at most twice because each switch re-sends the context without the other model's prompt cache. Compaction summaries go to the build model.

The dashboard's New session dialog has a **One model / Plan + build** switch. In Plan + build, choose a card (Plan or Build), then a model from the list and a thinking level on the ladder; the list shows only signed-in providers, with starred favorites and recent picks first. The strip above the message box shows the current setup and highlights the model working now. Click it to change models in a running session: a different single model, a different build level, or switching between a single model and the same pair applies from the next message, while a new pair or planning level restarts the agent on the same conversation. Single models and pairs can use any level their models support; only eval isolation and the auto route stay at xhigh. Pi passes the other model's thinking as plain text. This is not a measured saving; `/cost` attributes every request to the model that answered.

**Autocompact.** The `autocompact` feature (on in the Windows defaults) runs Pi's own compaction when a run settles above its threshold, 300k context tokens by default, on a model with a larger window. It is inference on the session model (priced there in `/cost` and `/report`), unlike the offline-refused context flag `compact`. `--autocompact-tokens N` (a whole number from 1 to 100000000, only with `autocompact` selected) sets another threshold, for example `bin/apex --autocompact-tokens 200000`; the dashboard's New session dialog has the same field. A threshold at or above the model's context window never compacts. Pi always keeps its most recent `compaction.keepRecentTokens` (20,000 by default) uncompacted, so a threshold near that value reports Pi's "Nothing to compact (session too small)" until older context exists; choose a threshold well above it. Waiting for the run to settle avoids aborting work in progress, so one long request can pass the threshold before compaction. Pi's built-in threshold near the full window remains the fallback.

### Unavailable/deferred

- Core `bg`: its owned detached services rely on Unix session leaders and process-group signals for survival and cleanup. Bun (like Node) exposes no Windows Job Object API, and `taskkill /T` by PID cannot prove ownership, so no Windows-native version that keeps the same guarantees is feasible here. Refusal before allocation is tested; Unix survival is not disguised as a Windows pass.
- Core `max` and `recovery`: unavailable in the Windows target. Their gate is the free-only offline policy (multi-attempt inference and provider retry settings), not a Windows limitation, so a Windows-native port would not change it; unchanged.
- Context `route`, `output`: Muse-specific; unavailable on the Windows target's models. `all` rejects if it would select these unsupported capabilities—choose supported names explicitly.
- OCI proposer execution, Harbor benchmarks and two-model performance/cost targets: deferred, not waived or completed.
- POSIX executable modes, FIFOs and Unix process groups: out of Windows scope.
- File-symlink proofs requiring Windows privileges: still unexercised when privileges are absent. Directory-junction, hard-link, ACL and rollback coverage remains active. No elevation is requested.
- Optional TypeScript diagnostics: no complete TypeScript checker is installed here, so that diagnostic path is unexercised; real JavaScript syntax diagnostics (Bun's transpiler in a child process, nothing executed) pass.
- Windows PowerShell 5.1 console (conhost): Pi's default `system` theme draws inline code, list bullets and other violet accents in ANSI palette slot 5, which that console's palette maps to its own background, so those spans look blank. Pick Pi's `dark` theme once via `/settings` (it persists; its truecolor violet was verified readable there). Apex does not rewrite Pi settings.
- Pi's exit hint prints `pi --session <id>`; resume with `apex --session <id>` to keep the Apex features. Pi also prints a static warning that Anthropic subscription auth in a third-party harness draws from extra usage; with the Claude Code identity rewrite the acceptance requests completed on the subscription login.

## Storage and recovery

Shaping, checkpoints and newly written learnings share atomic owner-only Windows `.apex` creation. Existing public `.apex` directories are rejected for private writes without silently changing ACLs. Back up/review any existing directory before migrating it; do not delete existing checkpoints just to make a check green. Private spills pin native ancestor handles, reject reparse/hard-link entries and retain exact hook-visible output. Checkpoint snapshots inherit the private root and preserve source bytes and the user's Git index; source ACL restoration, cross-process checkpoint locking and interrupted transaction replay are not claimed.
